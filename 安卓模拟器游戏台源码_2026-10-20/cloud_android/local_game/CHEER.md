## 二、原版数值

- 八卦顺序：乾、坤、震、巽、坎、离、艮、兑，配置每条均相同。
- 1 阶转换比例：生命 4%、攻防法各 2.6%；逐阶累加，10 阶为生命 27.5%、
  攻防法各 17.5%。数值直接读取 `cortege_cheer_config.csv`，不做拟合。
- 进阶消耗：2 阶 25、3 阶 50、4 阶 75、5 阶 108、6 阶 129、7 阶 158、
  8 阶 194、9 阶 230、10 阶 331 张乾坤符箓（1015）。
- 助阵神仙属性只按人物仙缘与被动法术后的数值参与传递，不递归计算其他助阵。
- 五星助阵可指定一个出战阵位作为受助对象；低星只能参与人物仙缘。
- 助阵神仙不进入出战队列，重新指定受助对象会解除该阵位原有唯一关联。
- `*_recover` 列：2 阶 0.5%、3 阶 0.7%、4–10 阶 0.9%；累计 7.5%。客户端将其
  作为洗练动态比例的读写字段（`getDynamicEffectPercents`），界面以
  `当前总比例 (动态比例)` 显示。

## 三、10 阶洗练

原版客户端可见流程：

1. 阵法达到 10 阶后，主界面按钮由 `upgrade1.png`（进阶）换成
   `succinct1.png`（洗练），右侧显示材料与元宝消耗。
2. 参考图 `IMG_3323.JPG` 明确显示洗练消耗为 **20 张乾坤符箓 + 10 元宝**。
   该数值来自服务端下发 `cost_item_count/cost_gold_count`，不在客户端 CSV 中。
3. 点击洗练发送 `stat_req`；服务端返回 `src_index`、`des_index`、`modify_value`
   与 `plus_level`。
4. 客户端以 `Mapping={2,3,1,4}` 将服务端 1–4 映射到生命／攻击／防御／法力，
   显示四项 `当前 (动态)`、`+x%`／`-x%`、`洗练后 (动态)`。
5. 接受发送 `succinct_confirm`，放弃发送 `succinct_abandon`；未确认前再次请求
   会被客户端阻止。
6. 洗练面板保留原版“阵位／被动”两页签；被动页展示助阵额外被动效能，并跳转
   已实现的演武堂进修，不伪造原版专属技能槽。

### 本地补充规则（服务端不可见部分）

随机区间与首轮可用来源不在 APK 内。本地采用可从原表直接推出的最小规则：

- 每次洗练在四个属性中随机选一个增加、另一个减少，二者不同。
- 单次转移比例 = 当前阶 `*_recover`，10 阶为 0.9%。
- 每个属性的动态比例限制在累计 `*_recover` 的 ±7.5% 内；四项动态比例之和恒为 0。
- 动态比例直接叠加到该阵位转换比例，再按原版向下取整传递给受助神仙。
- 洗练在生成结果时一次性扣除 20 张符箓与 10 元宝；放弃不返还，接受不再扣费。
- 原版进阶提示材料可在仙盟宝库兑换；本地未开放仙盟，主界面、进阶面板和洗练面板的
  消耗行均可点击，按既有本地价格 40 银两/张一次兑换 25 张乾坤符箓。
- 所有操作沿用 SQLite 事务与请求幂等；材料或元宝不足、重复请求、重试均不会
  重复扣费。旧存档没有 `dynamic/refine` 字段时按 0 和空值迁移。

## 四、存档结构

```json
"support": {
  "version": 2,
  "slots": {
    "1": {"hero": 5002, "target": 1, "level": 10,
          "dynamic": {"hp": 0, "attack": 900, "defense": -900, "magic": 0},
          "refine": null}
  }
}
```

`dynamic` 单位为十万分之一比例（900 = 0.9%）。`refine` 仅在待确认时保存
`{"gain":"attack","lose":"defense","rate":900}`。视图层同时输出
`base_ratios`、`dynamic_pct`、`ratios`、`next_increments` 与 `refine_cost`，
界面、面板、阵法加成和战斗读取同一份结果。
