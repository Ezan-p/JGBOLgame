日期：2026-10-23。对象：《金箍棒 online》APK 1061 + 项目已保存的1263更新资源。**原客户端和数据表已还原；原服务器代码与在线配置响应不在资源包内，不能据此宣称完整恢复官服结算。**

## 1. 证据及结论

主要证据：`lua/ui/equipAdvanceUI.lua`、`lua/data.lua`、`lua/ui/packageUI.lua`、`lua/ui/stoneUI.lua`、`lua/common/common_def.lua`、`lua/common/msg_def.lua`，三张CSV及 `v2/String.plist` / `String2.plist`。48份原文件、SHA-256、反编译文本、中文原文和结构化规则保存在 [证据目录](../安卓模拟器游戏台源码_2026-10-20/cloud_android/outputs/equip-advance-20261023/)。可执行 `scripts/export_equip_advance.py` 重导出。

升阶与强化是独立系统：强化改变 `level`；升阶使用 `advance_level`（阶）、`star_count`（本阶注灵星数）、`cur_spirit_count`（当前星进度）。这里的七星是注灵进度，区别于物品四星/五星品质，也区别于另一个 `msg_equip_rising_star` 装备升星协议。

- 原选择器仅列武器、防具、法宝且品质 ≥4，不排除已装备物品。
- 数据覆盖四星、五星、三种装备，共6组；每组有零阶零星到十阶的81个有效状态，共486个。
- 每阶先点亮七星，再消耗两种材料升一阶。十阶显示最高阶文案，隐藏注灵按钮，点亮七星，经验显示 `0/0`。
- 按钮操作发送 `msg_equip_advance=1073`；`flag=1` 注灵、`flag=2` 升阶，另传 `equip_order`、`equip_id`、`is_one_key`。一键注灵只改变布尔标志。
- 客户端注灵前校验对应精华数量；升阶前逐项校验两种材料。没有此系统的银两扣费字段，也未发现概率/失败补偿字段。
- 注灵成功播放进度增长；点亮新星使用 `shengjie.ccbi`，进阶成功使用 `shengjie02.ccbi`。

## 3. 属性表与计算

`equip_advance_worth.csv` 有大量重复的 `star1_worlth`…`star7_worlth` 列名，不能用普通字典CSV读取器解析。原版 `data.getEquipAdvanceValue()` 按列位置处理：跳过前两列后，以1开始编号 `n`，阶数=`floor(n/8)`，星数=`n%8`。八列一组，前七列是本阶七星，第八列是下一阶零星。零阶零星单独补零。

每个单元格的语义：`percent|plus`，升阶列为 `percent|plus|extra`。百分比和固定值都是当前状态的累计值，不能再次累计之前各阶。

七星阶段的每颗星固定值直接查原表，未线性拟合。例如法宝四阶内的附加值存在不等差增长，防具五阶内同样不是统一步长。

原版详情：设装备基础强化值为 `B`，灵石比例为 `S`，升阶表为 `P/F`，按独立项显示 `floor(B) + floor(B*S) + floor(B*P+F)`。升阶预览分别显示 `floor(B*P)` 与 `F`。灵石和升阶都以基础装备属性为基准，不能把升阶值再次乘灵石比例。

`extra` 在客户端仅提供三/六/九/十阶激活说明；本包没有证据确认它在服务器端对神仙基础属性的取值基数、是否累计、与仙缘等乘区的顺序。因此实现保留原文和激活状态，不额外猜加一个角色百分比，也不把该列重复加进已明确的装备 `percent`。

## 8. 「神·装备」与「鸿」标记：原版封神、铸造系统

补充日期：2026-10-23。截图参照：[IMG_3414.JPG](../素材图/IMG_3414.JPG)。**本节为逆向资料补充，不表示本地已实现封神、铸造或连锁结算；本次只更新本文档，没有修改游戏代码、资源包或存档。**

### 8.1 结论与字段分工

截图右侧三件装备是「神·盘古幡」「神·无极道袍」「神·紫金钵盂」。名称前的「神·」代表装备已经**封神**；右下角「鸿」代表封神装备的**鸿蒙铸造等级**。客户端脚本将封神称为 `equipAsc` / `equip_reborn`，界面原文则使用「封神」「神器」「铸造」。它们是普通升阶后的后续系统，不能把「鸿」当成普通第十一阶。

| 数据或表现 | 原版判定 | 含义 |
|---|---|---|
| 强化等级 | `level` | 截图左上角白字174、175等，与封神、铸造分开 |
| 普通升阶 | `advance_level`、`star_count`、`cur_spirit_count` | 本文第1～3节的十阶与注灵 |
| 名称「神·」 | 装备 `reborn_bit > 0`，调用 `getItemName(..., isAsc)` | `pre_item_name = "神·"`，拼接原装备名；显示过程不替换 `type_id` |
| 红色发亮边框 | `getSmallItemSprite` 的 `is_asc` 分支 | 叠加原图 `v2/ascCast/circle.png`，不是凭名称文字识别 |
| 「后 / 先 / 混 / 鸿」 | `cast_level = 1 / 2 / 3 / 4` | 铸造状态，优先于普通阶数牌显示 |
| 六星装备 | `star_level == 1` | 另一套装备升星状态；与五星品质、注灵星数均不同 |

仅改装备名称不会触发封神属性、边框或铸造。反过来，名称和红框由 `reborn_bit` 控制，不要求先达到鸿蒙；「神·」与「鸿」不是两个同义标识。`reborn_bit` 在这些显示调用点仅作“大于零”判断，不能据此推导其全部位定义。

### 8.2 封神条件、消耗与属性变化

证据：`equipAscUI.canAsc/pressAsc/create`、`packageUI` 装备详情、`equip_reborn_base.csv`。

| 环节 | 客户端可直接确认的条件 |
|---|---|
| 封神资格函数 `canAsc` | `g_is_open` 为真、装备品质恰好为5、`advance_level == MAX_ADVANCE_LEVEL` |
| 未封神装备的详情入口 | 普通升阶系统开放、当前详情允许强化操作、满足 `canAsc`、行者等级≥70、`reborn_bit == 0` |
| 点击封神按钮 | 主角 `reborn_layer == 0` 时拒绝并提示「主角境界不足」；因此正常状态需要主角至少一重境界 |
| 材料校验 | 三类装备均消耗补天石 `1333` ×20，逐次检查持有数量 |

`MAX_ADVANCE_LEVEL` 来自普通升阶在线配置，本地保存的完整属性表上限为十阶。因此现有证据对应「五星装备升至十阶后封神」，实现时仍应保留“达到配置上限”的真实判定。资格函数没有另加“十阶七星”判断，也没有把佩戴该装备的神仙转生次数作为条件；主角境界检查读取的是玩家数据。

原文 `cast2` 为「封神增强：」，并列展示「基础成长提高12%」「升阶系统提升为铸造系统」「开启神器铸造连锁系统」「开启神器套装系统」。补天石说明为「装备封神必备材料」，途径文本为「九幽玩法产出」；该途径文本不是掉率或完整产出规则。

三类装备基础成长配置分别为 `1|12`、`2|12`、`3|12`，对应攻击、防御、生命成长提高12%。原 `stoneUI.getEquipBaseEffect` 的实际公式为：

```text
A = base_gongji_plus + base_fangyu_plus + base_maxhp_plus
g = effect_plus
L = 强化等级
B普通 = A + (L - 1) × g
B封神 = A + (L - 1) × g × 1.12
B最终基础 = B封神 × (1 + (star_level or 0))
```

这里提高的是每级成长部分，不是将初始属性 `A` 一并乘1.12。最后一行是原函数对另一套装备升星字段的处理；截图的鸿蒙状态不能直接等同于 `star_level == 1`。

**封神后的初始铸造状态尚缺服务端证据。** 表确实有第1档“神装灵器×1”的记录；但铸造面板正常读取当前1～4档，封神结果页又同时存在 `cast_lv0.png` / `cast_lv1.png` 两个相同「后天」资源。事件回调只是刷新展示，没有给 `cast_level` 硬编码赋初值。因此不能宣称封神必定直接送第1档，也不能宣称封神按钮额外必扣1个神装灵器。能够直接确定的封神前端校验消耗只有补天石×20。

### 8.4 铸造与原升阶加成如何共存

虽然界面原文说「升阶系统提升为铸造系统」，`packageUI` 的详情计算仍先读取原 `advance_level/star_count` 的 `ad_effect`，封神时再读取 `cast_level` 的 `asc_effect`。封神分支将操作区替换成铸造区，但并未在此处删除原升阶加成。

以已经过封神基础成长处理的 `B` 为基准，详情分项为：

```text
floor(B)
+ floor(B × 灵石比例)
+ floor(B × 普通升阶比例 + 普通升阶固定值)
+ floor(B × 当前铸造比例 + 当前铸造固定值)
```

这些项共用装备基础值 `B`；不是先把普通升阶加成乘进去，再对结果乘铸造比例。以保留十阶零星的鸿蒙武器为例，客户端对应的两项分别是 `floor(B×1.05+791)` 与 `floor(B×0.50+525)`。这只是按指定字段推导的装备详情公式，不证明封神响应必然保留何种星数，也不等同于已恢复角色战斗属性、仙缘、套装等所有乘区。

本次已直接读取并查看原版PNG，不以截图中的模糊像素猜字或重画。小牌是40×40透明底圆形徽记；长牌是81×41透明底横向铭牌。

同图左侧法术的「悟」来自 `upgrade_level > 0` 与 `v2/enhanceUI/wu.png`，不是铸造字样；角色名字、角色境界或角色转生光效也不由装备 `cast_level` 决定。

### 8.6 神器套装与三件铸造连锁

封神还开放两种独立的组合展示，不能将它们当作「鸿」徽记本身的属性。

**神器套装：** `equipAscUI.getCortTierInfo` 只收集同一神仙所穿、`attach_type == item` 且 `reborn_bit > 0` 的装备类型ID，再匹配 `equip_reborn_fate.csv`。当前表有29组，其中16组三件套、13组两件套。多个组合同时匹配时，客户端选择所需件数最多的一组展示；原提示为「套装效果不可叠加」。该函数没有要求套装的每件装备均为鸿蒙。

截图的组合可精确对应到原表：

| 物品ID | 截图中的原装备 |
|---:|---|
| 2044 | 盘古幡 |
| 3003 | 无极道袍 |
| 4024 | 紫金钵盂 |

三件均已封神时命中第16组「天道元始」：`1|20/4|10`，即攻击提高20%、法力提高10%。其中盘古幡＋无极道袍也匹配第24组两件套「天道」（防御提高15%），但客户端按件数优先展示三件套，不会把两组说明简单相加。这是根据截图装备身份和客户端匹配规则的推导；截图本身没有展开套装属性页。

**神器铸造连锁：** `equipCastUI.getCortCastInfo` 要求同一神仙恰好有三件装备，以三件的**最低** `cast_level` 选择不超过该值的最高一行配置；不是平均等级或铸造等级之和。该函数以三件及其 `cast_level` 判断，未另检查每件的 `reborn_bit`。

| 最低铸造字段值 | 原表名称 | 攻击固定值 | 防御固定值 | 生命固定值 |
|---:|---|---:|---:|---:|

| 2 | 先天神器连锁(3件) | 1000 | 800 | 800 |

### 8.7 面板流程、特效与协议

封神页使用原 `v2/ascCast/bkg1.png`，黑色遮罩透明度180。上部左右并排显示普通装备与封神预览，保持原装备画面和品质星，右侧叠红框并在名称前加「神·」；下部左侧是补天石及持有量，中部是四项封神增强说明，右侧是确认按钮。两装备图标相对背景中心x偏移分别为 `-0.24w / +0.26w`，y为 `+0.19h`；关闭按钮位于 `(+0.43w,+0.44h)`。

铸造页使用 `bkg2.png`：左上装备及名称，右侧比较「当前 / 下阶」铸造等级和两项加成；下部按下一档材料数量均匀排布，持有量不足红色、足够绿色，右侧为铸造按钮。鸿蒙页替换为单档属性与满级提示。这里是封神、铸造独立窗口，不沿用普通注灵页的七星进度条。

封神成功展示依次调用 `shenzhuang_effect001.ccbi`、`shenzhuang_effect002.ccbi`，结束后显示新名称及铸造长牌；铸造成功使用 `zhuzao_effect001.ccbi`，随后显示当前档结果。这些是操作成功演出，与图标上的常驻升阶动画分开。关闭或结束刷新会回到对应包裹/阵容显示。

两个操作共用 `msg_reborn_event = 1328`：

| 请求 | `reborn_type` | `id` | `data` 中的业务字段 |
|---|---:|---:|---|
| 装备封神 | 3（equip） | 5（equip_reborn） | `equip_id`、`equip_order` |
| 神器铸造 | 3（equip） | 6（equip_cast） | `equip_id`、`equip_order` |

协议结构为 `serial_num=I,reborn_type=B,id=B,data=s`，`data` 使用原 `table.tostring` 序列化，不应擅自改称JSON。`ascensionUI.onGetResult` 按结果 `flag` 分发至封神、铸造界面播放演出。物品结构分别携带 `reborn_bit=B`、`cast_level=I`，普通升阶三字段也仍存在。
