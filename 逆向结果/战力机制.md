# 原版战力机制与本地接入说明

解析日期：2026-10-23。

**已确认单神仙战力和玩家总战力的来源、协议更新及显示路径；尚未取得原服务器的单神仙计算公式。不能据此宣称已完整复刻原版战力。** 本次移除本地首页原先的 `生命 + 攻击 × 3 + 防御 × 2`，接入明确的战力缺失状态，避免把自定义数值显示成原版战力。四维属性及现有战斗功能继续使用项目原有实现。

## 一 战力的四种口径

| 口径 | 原版字段或规则 | 能确认的内容 |
|---|---|---|
| 单个神仙 | `combat_power` | 由服务器神仙记录下发，不由角色 CSV 或阵容 UI 计算 |
| 玩家首页总战力 | `role_combat_power` | 登录资料及角色属性更新下发；首页直接显示 |
| 查看他人阵容的总战力 | `sum(cortege_list[i].combat_power or 0)` | 客户端对响应中的神仙列表逐项求和，这是已发现的明确计算公式 |
| 战报中的战力 | `floor(fight_data.src_info.role_combat_power)` | 战报快照中的攻击方战力，不能直接替代当前玩家战力 |

另外，更新版属性枚举存在 `role_property.max_combat_power = 39`；已确认字段存在，未确认其更新条件和完整业务含义，不能把它当作当前战力使用。`fight_power`、`fightpower` 还出现在领地、战报等显示路径，不能仅凭命名视为同一公式。

## 二 单神仙战力来源

### 完整记录

更新版 `lua/common/msg_def.lua:470` 的神仙结构包括：

```text
id, order, cheer_order, type, level, cur_exp, next_exp,
hp, magic, gongji, fangyu, combat_power,
culture_point, hp_plus, magic_plus, gongji_plus, fangyu_plus, ...
```

其中 `combat_power=I` 是单独的整数协议字段；与生命、法力、攻击、防御并列。四维和战力同时下发，不代表战力就是四维的线性加权和。

### 增量更新

`common_def.cortege_property.combat_power = 58`。`ui/lineupUI.lua` 的神仙属性更新处理按属性编号查枚举名称，再将收到的 `value` 写入对应字段。血量、攻击、防御、法力另有 `*_show` 字段映射；不能把战力字段编号 58 解释成计算系数。

### 显示和变化量

`ui/charPositionUI.lua:1922` 读取：

```lua
local combat = characterInfo.combat_power or 0
```

随后调用 `playerInfoUI.showCortegeCombatLayer`。同一页面保存 `g_lastCombat`，新值高于旧值时显示差值。这里的增加量是**两次服务器数值相减**，不是根据本次培养或装备效果推算战力。

`playerInfoUI` 负责数字图集、逐位拆分和动画，没有将四维转换为战力的公式。原版局部 UI 的 `or 0` 是缺字段显示兜底，不证明“没有原服公式的本地角色战力为零”。因此本地未知值显示“—”，而不显示伪造的零。

## 三 总战力来源和计算范围

### 首页

`role_property.role_combat_power = 30`。登录结构 `msg_def.lua:663` 包含 `role_combat_power=I`。

`lua/event_mgr.lua:1467` 的角色属性更新分支：

```lua
elseif msg_table.attr_list[i].type == r_p.role_combat_power then
    d_ms.d_mainUI.g_playerInfo.role_combat_power = math.floor(msg_table.attr_list[i].value)
    d_ms.d_mainUI.showCombat()
```

首页 `mainUI.showCombat()` 将该字段交给 `playerInfoUI.showCombatLayer`。`g_oldCombat` 缓存旧值；在首页、无其它面板且不处于祝福页面等条件下播放变化动画。动画不是重新计算。

**首页代码没有自行遍历背包或出战列表求和。** 虽然他人阵容页面采用求和，仍不能由此证明服务器 `role_combat_power` 在所有版本、模式下必然等于该求和；尚缺同一快照的原服数值对照。

### 查看他人阵容

`ui/checkLineupUI.lua:58,130–146`：

```lua
displayLineupInfo.usedCharacters, info.role_combat_power = sortCharacters(data_table.cortege_list)
-- sortCharacters 内
local sumCombat = 0
for i = 1, #cortege_list do
    sumCombat = sumCombat + (cortege_list[i].combat_power or 0)
end
```

具体规则：

- 求和范围是这次响应的整个 `cortege_list`，不是所有已拥有神仙。
- 没有只取前四名的限制；不能丢掉响应列表中的后备位。
- `cheer_cortege` 由独立的 `createCheerCharacters` 处理，不在这个循环里直接相加。
- 助阵可以通过改变出战角色属性间接影响服务端战力，但客户端求和不能证明其战力直接贡献率。
- 缺少某项 `combat_power` 时该项按 0 加，空列表为 0；逐项不额外乘站位或品质系数。

例：返回的八名神仙战力为 10、20、30、40、50、60、70、80，则该查看页面总战力为 360。额外助阵列表不直接加到 360 中。

## 四 属性来源与战力来源的区别

以下是原资源确认的养成配置和属性入口。它们说明四维属性或战斗效果从何而来；**不等价于已确认每种来源增加多少战力**。

| 来源 | 原始依据 | 可确认内容与边界 |
|---|---|---|
| 神仙模板和等级 | `cortege_base_0.csv`；`inheritUI/expbookUI` | 基础预览为 `基础属性 + 每级成长 × (等级−1)`。成长对应 `base_gongji_plus/base_fangyu_plus/base_maxhp_plus/base_maxmagic_plus`；不是战力权重 |
| 培养 | 神仙记录 `hp_plus/magic_plus/gongji_plus/fangyu_plus`；`trainingUI` | 已接受的培养结果改变四维加值；未接受结果不应作为当前属性。潜能点是培养资源，不是战力 |
| 飞升 | `evolve_level` 与养成界面 | 原界面展示每级各维增加对应基础成长的 3 倍；完整叠加与战力换算不能由此推出 |
| 转生和仙脉 | `cortege_reborn_effect.csv`、转生配置、`reborn_vein_level` | 存在固定加值和比例字段；服务端应用顺序及战力权重未确认 |
| 装备和强化 | 装备配置、`equipmentUpgradeUI` | 装备基础效果按 `base_*_plus + (level−1) × effect_plus` 展示；这是装备属性量，不是装备战力 |
| 灵石 | 灵石配置、`stoneUI` | 改变对应装备属性，具体规则见《装备详情与灵石机制》；不能再把灵石效果作为独立战力重复加一次 |
| 法术和升级 | `skill_base.csv`、法术详情页 | 属性被动与主动威力、概率、目标数是不同数据。属性效果和主动法术战斗价值不能共用一个未经证实的战力系数 |
| 人物、装备、法术仙缘 | `fate_config.csv`；`cortege_fate_* / equip_fate_* / skill_fate_*` | 激活条件、作用属性和效果配置可提取；不能证明服务器战力对仙缘另算额外分数 |
| 八卦助阵 | `cortege_cheer_config.csv`、八卦属性字段 | 关联及传递属性见《八卦助阵》；他人阵容总战力不直接加助阵列表 |
| 全局成长和收集 | `role_*_plus`、`role_collect_*`、`role_genius_*` | 协议枚举明确存在全局、收集与相关比例入口；完整运算需服务端证据 |
| 精魄、觉醒、星等扩展效果 | `ext_skill`、觉醒配置、`ext_star_config` 等 | 可能改变属性、法术威力或触发行为。是否以及如何折算进面板战力仍未知 |

尤其要区分 `*_show`（展示属性）、`*_calc`（计算属性）和战斗过程中的即时属性。协议同时定义这些不同字段，不能未经验证就假定战力仅使用某一组。战斗胜负、普通攻击伤害、法术威力、竞技排名分数也不是战力。

## 五 已排除的本地替代规则

旧版 `local_game/home.lua`：

```lua
if hero.active then power = power + hero.hp + hero.attack*3 + hero.defense*2 end
```

这是项目本地展示规则，既没有原版来源，也遗漏法力等可能相关因素。**不能因为删除了这个公式，就宣称已经找到了原版公式。** 本次不拟合任何新权重，不增加品质、技能或装备的猜测战力。

当前本地属性链为：等级基础值 → 装备/灵石/法术等本地计算 → 培养加值 → 仙缘 → 助阵。`service.py`、`inventory.py`、`synergy.py` 存在不同的取整和叠加实现；本次没有将这些现有实现认证为原服完整属性算法，也没有改变战斗伤害模型。

## 六 本地接入范围

| 位置 | 本次行为 |
|---|---|
| `local_game/power.py` | 原协议整数读取和校验；他人阵容列表的原版求和函数；本地战力缺失状态 |
| `service.Game.view` | 返回 `power.status=unavailable`、原因和当前四维快照；每名神仙标记 `combat_power_status`；清除展示副本中无依据的旧战力值，不修改存档 |
| 首页 | 消费 `role_combat_power` 数值字段；当前无原服来源时显示“—”，点击说明“暂不可用” |
| 阵容 | 增加单神仙战力显示位置，缺失时显示“—” |
| 保存和养成 | 不添加战力存档缓存，不用旧快照覆盖升级/换装后的属性；保持现有玩法 |

原版的他人阵容求和函数已经实现并测试，但当前本地服务没有原服查询通道，不能凭空调用它生成有效战力。也没有通过自定义状态字段导入旧数值的后门。完整原版计算接入仍未完成。

## 七 证据和复现

证据目录：`安卓模拟器游戏台源码_2026-10-20/cloud_android/outputs/power-20261023/`。

- `sources.json`：实际解析资源名、版本、文件名、SHA-256，以及反编译文本哈希。
- `evidence.json`：战力关键调用及协议的带行号摘录。
- `scan.json`：项目 `Resources` 解析视图中 289 个 Lua 和 379 个 CSV 的关键词扫描结果。没有 CSV 命中 `combat_power/fight_power/fightpower`；这不是对所有可能别名的数学排除证明。

版本范围为 APK 1061 与项目已保存的更新资源覆盖。不同文件可能来自不同版本，须逐项读取来源清单；不把未下载的更新资源声称为已分析。已有更新版首页缓存也确认直接使用 `role_combat_power`。`runeUI` 新提取版本在 LJD 中触发断言，来源清单保留错误，相关界面只作为旧反编译辅助线索，不用于证明公式。原生库字符串搜索未找到对应战力符号，这不足以证明任意机器码中都不存在相关计算。

在 `cloud_android` 目录执行：

```sh
.runtime/venv/bin/python scripts/export_power_research.py
.runtime/venv/bin/python -m unittest discover -s tests -p 'test_power.py'
```

导出工具调用项目已有 LJD，不改原 APK、玩家存档或原渠道数据。反编译存在工具局限，因此结论限定为已经核实的协议读写、字段和显示逻辑，不以“全文搜索不到”推导不存在服务端算法。

## 八 完整复刻仍需的证据

要完成“严格按原版计算”，至少还需原服务器战力函数，或可验证的原服受控样本：同一神仙在仅改变一个因素前后的完整神仙记录、玩家总战力、出战/后备/助阵列表。应覆盖生命、攻、防、法、主动/被动技能、培养、装备、灵石、仙缘、转生和全局加成，并包含取整边界。

用样本求得候选公式后，必须在未参与拟合的神仙和组合上验证，并核对首页总战力与列表求和是否一致。单张面板截图或一组总战力无法唯一确定系数、叠加顺序和取整规则。取得这些证据前，未知值保留为未知。

## 九 验证结果

新增 3 项战力测试覆盖协议零值与非法值、八名神仙求和、首页字段独立性、本地未知状态、升级刷新及展示不改写存档。全量 136 项测试通过。APK 已构建、通过签名校验并覆盖安装到现有模拟器；首页与阵容页已检查。安装前备份位于 `.runtime/local_game/power-validation/save-before.sqlite3`，资产、神仙和进度保持一致，正常登录只更新 `saved_at/energy_time`。

这些测试验证本次接口与显示处理，没有原服基准样本，因此不构成原版战力数值一致性验证。
